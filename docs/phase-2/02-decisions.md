# Phase 2: decision log

Continues the numbering of [`../phase-1/02-decisions.md`](../phase-1/02-decisions.md) (D1 .. D33). Each decision: Context, Decision, Alternatives considered, Consequences.

**D34 Feedback enters through a REST endpoint and a Temporal signal; the service never generates it.** Context: the owner will test and demo by hand, and load-test with a Python simulator; the instruction guide forbids mock data in the project. Decision: `POST /workflows/{workflowId}/feedback` sends a signal; the workflow waits for it in an `await-feedback` step; no feedback within the timeout is `NO_RESPONSE`. Alternatives: activities returning random or scripted results (mock data, rejected by the owner); activity results fed by an external system (would need a callback channel). Consequences: this brings the guide's Phase 3 idea (signal plus await with timeout) into Phase 2 because the feedback has to come from outside; activities stay log-only and return nothing. The simulator is a client of the same endpoint.

**D35 Day 0 / Day 1 / 15 days.** Context: "workflow triggered = Day 0, communication starts the next day, nothing after 15 days". Decision (owner chose calendar days with a fixed hour): Day 0 is the IST date of the run start; Day N is N days later at `sendHour` (10:00); the window ends at the end of Day 15 (00:00 of Day 16, exclusive), so all of Day 15 is usable. All of it is in the YAML `campaign:` block. Alternatives: rolling 24 h from the trigger (times drift); trigger time + 15 x 24 h (the owner preferred end of Day 15). Consequences: a workflow triggered at 23:50 gets its first contact in about 10 hours; one triggered at 00:05 in about 34 hours. Day 0 comes from `WorkflowInfo.getRunStartedTimestampMillis`, which is in the history, so replays agree.

**D36 Anything that would cross the window is dropped, and the workflow ends normally.** Decision: a `delay` computes its wake-up time and, if it is outside the window, does not sleep: `WF_WINDOW_EXPIRED` is logged and the workflow completes (status COMPLETED, not terminated). `contact` and `activity` steps also check before sending; an `await-feedback` is cut at the deadline. Alternatives: sleep until the deadline and then end (holds a timer for no reason); fail the workflow (it is not an error). Consequences: "remind me in 20 days" ends the workflow at once, on the day the customer asked, without a timer.

**D37 Two new step types: `contact` and `await-feedback`.** Context: the contact must go out on a channel that is only known at run time (DB channel, the customer's reminder channel, the channel of the last contact), and the activity depends on the channel. Decision: `contact` takes a `channel` (a literal or a path), picks `executeVoiceCall` for VOICE and `sendMessage` for WHATSAPP / SMS, and records the channel used. `await-feedback` waits for the signal. The `activity` step type stays for explicit use. Alternatives: a `switch` on the channel in front of every contact (a lot of YAML); a dynamic activity name in `activity` (a hole in the fixed registry, D7). Consequences: the Phase 1 `route` switch and the two first-step branches are gone; the first contact is one `contact` step with `channel: customer.initialChannel`.

**D38 Run variables instead of expressions or step-result storage.** Context: the guide's Phase 2 sketch stored results per step id (`voice-call.outcome`). Here the feedback is not the result of one step, and the reminder values must survive several loops. Decision: a small fixed set of readable paths (`RunPaths`): `customer.*`, `feedback.type|remindAfter|channel`, `reminder.after|channel`, `last.channel`. The engine sets them; the YAML reads them in `switch.on`, `delay.fromVar` and `contact.channel`. Alternatives: per-step results with `${step.field}` (more general, more machinery, not needed yet); an expression language (the guide forbids it). Consequences: `fromResult` and `${...}` from the guide are not built. A REMIND_LATER that leaves a value out keeps the earlier remembered value, which is how "remind again with the same duration and channel" works.

**D39 Defaults live in the YAML.** Decision (proposed by the assistant, accepted by the owner): reminder time 1d (`delay.defaultDuration`), reminder channel the DB channel (`contact.defaultChannel`), no-response retry after 1d on the DB channel, inconclusive follow-up after 1d on the last contact's channel, feedback wait 2h. Alternatives: Java constants or `application.yaml`. Consequences: changing a default is a YAML edit (and a hot reload).

**D40 `campaign.dayLength` for demos and load tests.** Context: a 15-day campaign cannot be demoed or load-tested in real time, and the guide forbids a `durationSeconds` override on the API. Decision: an optional YAML field; when set (e.g. `2m`) one "day" lasts that long: Day N starts at the trigger + N x dayLength, the window ends after `maxDays` such days, and whole-day durations (`1d`, a customer's `2d`) are scaled the same way. Not set (the shipped file) = real calendar days. Consequences: it is a deliberate extra (not in the instruction guide) and, like the 1m delay of the load tests, it must not be committed in the shipped YAML. In this mode contacts are not aligned to day boundaries, so a customer who never answers gets fewer than 15 contacts (each cycle is `1d + feedback timeout` long); with real days it is exactly one per day.

**D41 No retry cap.** Decision: the 15-day window is the only limit. A customer who never answers is contacted once per day on Day 1 .. Day 15 (15 contacts). Alternative: a maximum number of attempts per kind. Consequences: simple, matches the owner's description; add a counter step type later if a cap is wanted.

**D42 Feedback that arrives when no contact is waiting for it is dropped.** Context: the endpoint cannot know what the workflow is doing. Decision: queued feedback is kept while a contact is being made and until an `await-feedback` takes it; feedback queued before a `contact` step starts (for example sent on Day 0 or while waiting for a reminder) belongs to no contact and is dropped with `WF_FEEDBACK_DROPPED reason=STALE_BEFORE_CONTACT`. The endpoint still answers 202 because the signal was delivered. Alternatives: keep it and apply to the next contact (a stale answer would decide a later contact); reject it (needs a workflow query on every call). Consequences: a simulator must send feedback after the contact it answers. Seen in the manual run: a POSITIVE sent between two reminders was dropped.

**D43 `SMS` is a contact channel but not a customer channel.** Decision: `Channels` = VOICE, WHATSAPP, SMS for contacts and for `feedback.channel`; the table column and `customer.initialChannel` stay VOICE / WHATSAPP (D11, no DB change). The thank-you is sent with channel SMS through `sendMessage`. Consequences: a customer can ask to be reminded by SMS.

**D44 Transition cap 500.** Phase 1 had 100 (D22). A campaign loops about 4 steps per day for 15 days; 500 leaves room and still stops a runaway loop.

**D45 Hot reload is a folder rescan; "runtime editing" means editing the file.** Context: the guide lists YAML editing at runtime and hot reload for Phase 2 and the owner asked for them. Decision: the loader rescans every `orch.definitions-reload-seconds` (10) and on `POST /workflow-definitions/reload`; a valid file goes live, a broken one is reported and the previous version of that file stays live; startup is still fail-fast (D5, D16). Running workflows keep their snapshot (D1). Alternatives: upload or edit API (writes files from HTTP; not asked for); watch service (platform-dependent on WSL/Windows mounts). Consequences: no API can change a definition; the file is the source of truth. A half-written file is simply reported and picked up on the next scan.

**D46 Workflows started by Phase 1 code are not compatible with Phase 2.** A running Phase 1 workflow (old YAML as input, no `campaign`) keeps working only with the Phase 1 code; replaying it with this code is not supported. This is a proof of concept: wipe or finish Phase 1 workflows before switching branch (`docker compose down -v` or wait for them).

**D47 Branch and merge model.** `phase-2-feedback-switch` was created from `phase-1-start-all`, which already contains `phase-1-done`, the `start-all` endpoint, IST logs and the load-test tooling. The owner asked for the Phase 1 branches to be merged into the Phase 2 branch; no merge commit was needed because `phase-1-channel-routing` and `main` are ancestors of `phase-1-start-all`. `main` is unchanged until Phase 2 is accepted and tagged `phase-2-done`.

**D48 Tests.** Plain JUnit as in D15. Workflow tests send the same signal the endpoint sends and use the real log-only activities; there is no mock feedback source and no mock data in the project. The test-only `RecordingActivities` gained the channel of each call.

**D49 Readable conversation log, in the main log and in `logs/conversation.log`.** Context: the `event=` lines are built for scripts and the business lines were buried in them. Decision (owner chose both places, with date and time in each line): `Sending/Calling <CHANNEL> to <customer> (<phone>) [<step>] at <date time IST> >> <text>`, `Customer <id> replied at ... >> <type> (...)`, `Campaign for <id> ended at ... >> <outcome> after <time>, <n> contacts (<channels>)`. They go through the logger `conversation`, which logback sends to the main log and to a second rolling file. Alternatives: change only the existing lines (no separate file); one log file with a shorter pattern for everything (would break the parsed format). Consequences: the Phase 1 lines `Voice call:` and `Send message:` no longer exist (nothing parsed them); `logback-spring.xml` now exists, so logging is configured partly in XML and partly in `application.yaml`; phone numbers appear in the conversation lines as they did in the old business lines.

**D50 Tests do not depend on demo edits of the shipped YAML.** Context: the working copy of `outreach-default.yaml` is shortened for demos (`dayLength`, short timeouts), which broke 14 tests that assert real calendar days. Decision: tests read the file through the test helper `ShippedYaml`, which removes the `dayLength` line and sets feedback timeouts back to `2h`. One test still loads the working copy as-is to prove it is valid. Consequences: a demo edit cannot fail the suite; a real change to the YAML still does.

**D51 Stop after 2 unanswered reminders: one final SMS reminder, then complete.** Context: with no retry cap (D41) a customer who never answers is reminded until the window closes (about 7 reminders for a 2-day reminder, about 14 for a 1-day one). Decision (owner): after two reminders in a row get no response, wait the reminder interval once more, send one final reminder by SMS and end the workflow (COMPLETED). A customer reaction to a reminder (a new REMIND_LATER, or INCONCLUSIVE) resets the count. Implemented with a new generic `count` step type (named counter, `reset`, or `limit` + `whenReached`) and four YAML steps. Alternatives: a hard-coded reminder counter in Java (not editable in YAML); sending the final SMS immediately after the second timeout (the owner did not say; the same interval as the reminders was chosen so the final reminder arrives when the customer expects a reminder, easy to change by pointing `whenReached` at `final-reminder`). Consequences: the limit (2), the final text and the channel (SMS) live in the YAML. See D52 for the first-contact no-response path. The final reminder is also subject to the 15-day window and is dropped if it would fall after Day 15. Counters are run state, rebuilt on replay like the other run variables; the engine logs `WF_COUNTER`.

**D52 The same rule for a customer who never responds (supersedes the no-cap behaviour of D41 for that path).** Context: after D51 a customer who never answered the first contact was still retried daily until Day 15 (15 contacts). Decision (owner: "keep it same"): one counter, `unanswered`, counts contacts with no answer in a row on both paths. On the first-contact path the first contact plus 2 unanswered retries (limit 3) lead to one final SMS the next day (same text and step as D51's) and the workflow completes: contacts are first contact, retry, retry, final SMS on Day 1 to Day 4 (all at 10:00). On the reminder path the limit stays 2 (D51). Any reaction (a REMIND_LATER or INCONCLUSIVE feedback) resets the counter. Alternatives: limit 2 on the first-contact path (only one retry; the owner's words were "2 unanswered reminders", and the retries are the reminders of that path, so the first contact is not counted as one); a separate counter per path (not needed: a reaction resets, and reminders only exist after a reaction). Consequences: no customer receives more than first contact + 2 retries + 1 final SMS without reacting, so the 15-day window is now only the outer bound for customers who keep reacting; the INCONCLUSIVE follow-up loop is still bounded only by the window because each loop needs a customer reaction. Change the limits in the YAML (`limit: 3` in `count-unanswered-contact`, `limit: 2` in `count-unanswered-reminder`).

**D53 Flag to log only the communication.** Context: the owner wants to read the conversation without the `event=` timing lines and the framework output. Decision: `orch.logging.communication-only` in `application.yaml` (default `false`, environment variable `ORCH_LOG_COMMUNICATION_ONLY`). When `true`, a Logback `TurboFilter` (`CommunicationOnlyFilter`, wired in `logback-spring.xml`) drops every log call except the `conversation` logger and WARN and ERROR, in the console and in both log files. Warnings and errors stay visible on purpose so a real problem is never hidden. Alternatives: setting `logging.level.root` (cannot let the conversation logger through the same way and hides errors too); a separate profile (a second config file to keep in sync). Consequences: with the flag on, the `event=` lines are not written, so the load-test report script has nothing to read: keep the flag `false` for load tests. The Spring startup banner is not a log call and still prints (`spring.main.banner-mode: off` hides it). A change needs an app restart (no hot reload for logging settings). Checked on a real run: flag on gave 0 INFO lines in the console and the file, flag off gave 23.
